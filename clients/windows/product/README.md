# Oracle Proxy integrated Windows candidate

This is the product integration under development, separate from the historic deny-only LabManager. **It has not passed release acceptance and is not a GA distribution.** The initial workflow intentionally uploads source/build hashes only, not runnable binaries.

Target: Windows 10/11 x64. The WinForms desktop and SYSTEM service use one self-contained .NET executable. First setup requires UAC to install the fixed, auto-start SCM service and protected files; everyday login/connect/disconnect uses an owner-authenticated local pipe. No WireSock, official WireGuard GUI, FlClash or daily SSH is required. Backend: administrator-issued accounts only; native HTTPS automatic public-key enrollment and per-account telemetry.

The separate userspace WireGuard/TUN core is built from pinned sing-box v1.14.3 source with `with_gvisor,with_wireguard`. Its child-process interface accepts one configuration frame on anonymous stdin and closes gracefully on EOF. It has no exposed configuration server, shell, user-selected path or client-supplied endpoint. Application payload routing ends at the WireGuard endpoint; identified GameViewer program paths use the direct outbound. Upstream embeds Wintun; verify its signed driver provenance as part of Windows acceptance. This is a custom application embedding an open-source core, not an independently invented VPN cryptographic protocol.

The native Windows SDK WFP component owns one provider/sublayer and persistent ALE filters plus boot transport filters. It blocks other application egress, permits the TUN, loopback, DHCP/NDP, SYSTEM-only service/core identities, and verified UU paths. Transactions replace/remove only this provider's filters. A process/GUI crash must leave persistent filters in place. Presence/count inspection is only an invariant, not sufficient proof of every traffic path: actual packet and fault tests are required before release.

Keys/tokens are DPAPI CurrentUser encrypted **under LocalSystem** in protected ProgramData storage; the UI never receives the private key/token. Passwords are forwarded through the authenticated pipe only for login and not persisted. The service generates X25519 locally; the backend receives only its public key. Managed string copies cannot be reliably erased; memory-only configuration and zeroed byte buffers reduce exposure, not defeat a malicious SYSTEM administrator.

UU discovery reads local machine installation records and running processes, independent of drive letter. Only validated NetEase-signed executables under protected directories become process-path exceptions. Signature/publisher changes require refresh/review, not a broad filename bypass. Current publisher allowlist still requires verification against actual 4.39.2/4.41.1 installers. User-specific/writable installations must not silently receive SYSTEM path exceptions.

Known acceptance gaps: native SDK/Go/.NET compilation is being validated; real service setup/upgrade/rollback/uninstall and authenticated pipe negative cases; driver and full-device WFP packet behavior for TCP/UDP/DNS/physical IPv4/IPv6; abrupt service/core/GUI crashes; BFE restart and actual Windows boot; real UU controller/controlled-device continuity for the user's versions. Current Oracle client descriptor explicitly blocks IPv6 pending server-side IPv6 provisioning and dual-stack acceptance. No real restart/UU/IPv6 success may be inferred from a same-boot unit test.
