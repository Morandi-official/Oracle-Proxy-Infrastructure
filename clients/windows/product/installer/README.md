Oracle Proxy provides two distributions built from the same pinned payload:

- The portable ZIP contains the GUI, core, guard, corresponding licenses and build metadata. Its first service installation still requires Windows administrator approval.
- The Inno Setup EXE installs the desktop files to the fixed protected `Program Files\OracleProxyDesktop` directory, creates a Start menu shortcut and a standard Apps/Control Panel uninstall entry. The product verifies a protected Administrator/SYSTEM-owned desktop directory and a fixed product marker before installing executable files. A pre-existing writable or foreign directory is rejected, never silently adopted. It installs the same shared system service to the existing protected `Program Files\OracleProxy` directory.

Build order in the Windows hosted workflow is `package-candidate.py`, then `build-setup.py --iscc <installed Inno Setup 6 ISCC.exe>`, then `test-setup.ps1 -SetupPath <candidate setup.exe>`, then artifact upload. Use a known installed compiler; this build script never downloads a compiler or runs files from an arbitrary dist directory. The exact portable ZIP checksum, embedded metadata and all three executable/DLL hashes are verified before staging. The EXE includes the compiler/runtime license copied from that compiler's `license.txt`, its source URL and compiler hash.

The external `BUILD.json` gains an `installer` record only after the EXE compiles. Its `publisher_signed` value remains false; its installer digest is independently verified before CI execution. The portable/source ZIP metadata describes the pinned original payload and therefore does not recursively contain the outer installer record. The final outer `SHA256SUMS.txt` covers both ZIP archives and the Setup EXE. No test harnesses, DPAPI files, test accounts or secrets enter either distribution.

The standard installer resolves a new installation's owner from the current real Windows desktop session through WTS, rather than an environment username or the elevated administrator identity. A headless session is rejected. Administrators can use `/OwnerSid=S-1-...` for unattended installation, which invokes the fixed `--install-desktop SID` boundary. Existing installations retain their protected owner file and SYSTEM DPAPI state when upgraded.

Service installation/upgrade runs before desktop file replacement, through the product's existing pin checks, SCM identity checks, protected file transaction and service rollback. A failed service upgrade stops Setup without replacing the desktop. If later desktop file copying fails or Setup is forcibly terminated, the healthy service and protected state are retained; rerun Setup to repair the desktop. Do not claim an all-filesystem atomic transaction. Inno handles its own desktop file rollback; the product service keeps its previous signed/pinned rollback payload separately.

Uninstall first calls the fixed installed desktop CLI's `--uninstall`, after the user confirms and before Inno removes any logged files. The existing product boundary refuses a foreign service image and requires a verified disconnect before deleting its own guard, service and local DPAPI state. Inno's `usUninstall` callback treats exceptions as fatal, so an unsafe service removal leaves the desktop/uninstall entry available for recovery. There is no arbitrary elevated shell or custom command input. Server accounts and registered devices are not deleted. Portable and installed clients share this service: removing it also means a retained portable ZIP must reinstall the service before use.

Neither portable packaging nor a conventional Setup EXE eliminates SmartScreen reputation prompts. Do not add self-signed root certificates, unblock downloaded binaries globally, disable Defender/SmartScreen, or fake a publisher. A real trusted code-signing service/certificate and timestamped Authenticode signatures are a separate release gate; sign native payloads before embedding their hashes, then the final GUI, installer and Inno uninstaller using the same verified publisher policy. Windows UAC for installing the SYSTEM VPN service remains expected even with a trusted signature.

The hosted fixture performs a fresh silent EXE install, an actual second upgrade, SCM image/PID/autostart and installed-byte checks, owner binding, Start menu and Apps metadata checks, encrypted non-account state preservation, and an actual silent standard uninstall. It does not claim a physical reboot, a real desktop UAC interaction, third-party AV reputation, or signing acceptance.
