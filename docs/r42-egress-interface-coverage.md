# R42 — IPv4/IPv6 egress-interface coverage invariant

The second noncritical Windows test PC's **read-only** R40 observations
reported one active physical adapter, zero other active adapters, and one
IPv4 plus one IPv6 default route. These *counts alone are not a WFP
attestation*. This branch does not hard-code adapter identities or use
identifying network data from the operator's PC.

## New invariant

A future trusted LocalSystem kernel must independently observe the **current**
set of IPv4 and IPv6 default-route interface indices, match all of them
against actual WFP-protected interface indices, verify all up interfaces
are classified, and verify that DNS traffic on every interface is blocked
or routed safely. Missing or ambiguous interface indices, duplicate
indices, absent IPv6 coverage, unknown interfaces, stale snapshots or
new unprotected adapters fail closed.

The production transaction model now calls this separate interface-scope
audit before any key opening/tunnel start, immediately after native data
proof, before Off staging, and again immediately before owned-filter
release. A route appearing on an unguarded physical or virtual adapter
blocks connection or release even if unrelated WFP metadata looks healthy.

### Boundaries

The new contract is **not an implementation of the OS queries**.
`UnavailableProductionKernel` returns no evidence. All positive
interface-scope values in Windows CI are generated by an *in-memory fake*
and must not be interpreted as an existing full-device kill switch. The
real Windows BFE preflight from R35 is read-only and also cannot supply this
proof. The actual kernel will need trustworthy snapshots and atomicity or
event-driven enforcement to prevent time-of-check/time-of-use leaks as
interfaces appear, routes change and the service restarts.

R4 Windows CI tests: single adapter, extra missing IPv4/IPv6 interface,
duplicates, unknown adapters, missing DNS protection, stale snapshots,
and a route becoming unguarded just before explicit Off. The transaction
must never release WFP in the last case.

No production WFP mutation, WireGuard startup, Oracle/WireSock/UU change,
or test-PC modification is performed. Issue #34 stays open.
