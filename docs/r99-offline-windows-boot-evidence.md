# R99 — independent Windows NT boot witness, prior to actual isolated WireGuardNT / WFP

**Authorization:** The user approved free, isolated GitHub cloud Windows VM experiments (including genuine WireGuardNT/WFP after safety gates). R97 succeeded in disposable host-controlled QEMU guest hardware reset and qcow2 disk overlay rollback, but explicitly **did not prove** the Windows NT kernel had booted. R99 adds a distinct and stricter prerequisite. The Microsoft evaluation VM remains `-nic none`; R99 does **not** yet install a driver, enable a VPN, add WFP rules or touch Windows execution policies.

A preloaded Windows Server 2025 evaluation VHD does not include our trusted serial-response agent. Injecting privileged boot executables or silently bypassing Windows startup policies to answer a one-time host serial challenge would undermine the intended security proof. R99 instead reads native Microsoft Windows System event log records from the *powered-off guest disk*, using a separately controlled Linux host and a strictly read-only Linux loop/NTFS mount of an ephemeral RAW conversion. The original `guestfish` appliance failed even on an empty synthetic disk in GitHub CI, so it has not been accepted as evidence.

Microsoft officially identifies System event 12 from `Microsoft-Windows-Kernel-General` as Windows OS startup and event 6005 from `EventLog` as the start of its event log service: [Microsoft boot log troubleshooting](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/troubleshoot-unexpected-reboots-system-event-logs).

## Evidence standard

1. Confirm the public GitHub repository and standard hosted Ubuntu runner. Use Microsoft's official evaluation VHD, `QEMU/KVM`, an independent disposable QCOW2 overlay, no guest NIC and no public QMP/VNC port.
2. Before guest start, **read only** extract any baseline `Windows/System32/winevt/Logs/System.evtx`. If not present in the uninitialized evaluation image, do not fabricate it.
3. Timestamp the independent Linux host start/end interval, run isolated virtual hardware, externally reset guest once and shut it down.
4. With QEMU no longer running, **read only** extract `System.evtx` from the overlay, no Windows executable or guest agent required. Ubuntu 24.04's signed `python3-evtx` 0.7.4 distribution package is installed with all runtime dependencies. The earlier PyPI `--no-deps` wheel left the EVTX parser unable to import.
5. Require two corroborating, fresh records: Kernel-General event ID 12 followed by EventLog event ID 6005. Both require Windows provider identity, monotonic record IDs beyond any baseline, UTC timestamps within a short bounded host-observed interval and changed guest event log content. Stale, fake, partial, wrong-provider and unchanged log records fail closed.
6. Only after this proof may the isolated hypervisor reset-and-overlay-recreation path conclude. Every virtual disk and extracted guest log is deleted in ephemeral job cleanup. CI prints only verdict/counts, not guest log contents, addresses or secrets.

A fail or inability to mount an official VHD/overlay produces `R99_...DENY` or a failed job; there is **no fallback to QMP/framebuffer SHA hashes** as a substitute for genuine OS startup. Even a valid event pair is *not a guest-initiated reboot*. For later stage, Windows native WireGuardNT and WFP would need separate isolation, bounded keys, independent virtual NIC packet witness, stable driver signing, rollback and timeouts; none of those are claimed here.

The positive witness confirms actual kernel/eventlog activity during the cloud trial, but is not a cryptographic remote attestation of the trustworthiness of the entire guest OS. External platform and image identity remain crucial. R83 field native refusal, compiled production `UnavailableProductionKernel`, and GA Issue #34 remain unchanged. No physical computer, WireSock/UU environment, Oracle `wg0`/OCI NSG, DNS/routes or Windows execution policy is modified.

**Costs:** Only standard free GitHub Actions on this public repo, no paid/larger runner, no new provider, no artifact/cache/persistent Windows disk, no purchased Microsoft license or signature. QEMU nested virtualization is experimental and not an SLA.

## Revised host extraction path and verified prerequisite

R99 originally tried `libguestfs` OS autoinspection and explicit filesystem enumeration. Both failed; a separate tiny blank-disk libguestfs smoke on GitHub runner also failed with an appliance launch error. **This proves a host tooling limitation and says nothing by itself about Windows guest NT startup.** We do not weaken Windows or GitHub host security settings to coerce that appliance.

An independent standard GitHub-hosted Linux CI [run #39110124352](https://github.com/Morandi-official/Oracle-Proxy-Infrastructure/actions/runs/39110124352) instead validated a synthesized NTFS partition can be mounted strictly RO through an exact-owned Linux loop device, then unmounted and detached with zero residual. R99 now uses `qemu-img convert -O raw -S 4k` to create *disposable sparse clones only after QEMU has stopped*. It attaches the clone to a read-only loop, tests at most 16 bounded NTFS partitions for `Windows/System32/winevt/Logs/System.evtx`, and copies the bounded file to temporary Linux host storage. All loop mounts are closed in `finally` or exact-owned shell trap cleanup. The real guest VHD and QCOW2 backing remain unchanged.

The native Windows event-corrobation gate remains unchanged: absent/old/unreadable events must fail R99. No WireGuardNT, WFP or virtual guest NIC may be activated before genuine Windows kernel evidence passes. The next real VHD attempt is an experiment, **not** a passing kernel boot, real guest reboot or production authorization until CI actually verifies it.

## 2026-10-18 parser dependency regression and safeguard

[Real R99 Windows job #39110789996](https://github.com/Morandi-official/Oracle-Proxy-Infrastructure/actions/runs/39110789996) **failed closed after successful offline extraction of a Windows guest `System.evtx` file** with `R99_OFFLINE_LOOP_GUEST_SYSTEM_EVTX_EXTRACTED_READ_ONLY`. The crash was `ModuleNotFoundError` while importing `Evtx.Evtx`, because the prior hash-pinned PyPI package was deliberately installed with `--no-deps`, omitting its runtime modules. This result is **not** a successful NT kernel boot attestation. The remedy is to use the Ubuntu-maintained `python3-evtx` parser plus its Debian/Ubuntu signed dependency closure, accepting only the reviewed version family `0.7.4-*`. A separate `evtx-runtime-dependency-smoke` CI job validates the real Python import **before** the large official VHD job. Do not silently disable dependency checks, import arbitrary third-party wheels or convert parsing exceptions to affirmative boot status.

Only aggregate counts of recognized boot records (within/older/newer than the independent Linux UTC window) appear in CI; XML, exact event times and guest files are never uploaded. **Both fresh Microsoft-provider IDs must still corroborate one another**, and all failure paths remain fail-closed. ## Longer observation result and next firmware diagnostic

The longer actual GitHub [CI #39112692136](https://github.com/Morandi-official/Oracle-Proxy-Infrastructure/actions/runs/39112692136) also failed closed: R99 copied and parsed a valid Windows `System.evtx`, but **no** Kernel-General 12 or EventLog 6005 existed at any timestamp, despite a five-minute initial QEMU run and 150 seconds after a host hardware reset. The metadata-only summary reported all eight recognized-boot-event counters as zero. This distinguishes the issue from Python dependencies, NTFS access and a mere local/UTC offset. **The observed absence does not prove firmware is the cause**; setup/OOBE stages may be incomplete.

Before another expensive Windows run, R99 now attaches only its immutable official VHD-derived disposable sparse RAW clone via an exact-owned RO loop, mounts any bounded FAT/EFI partition with `ro,nosuid,nodev,noexec`, and prints only whether `EFI/Microsoft/Boot/bootmgfw.efi`, `EFI/Microsoft/Boot/BCD` and standard fallback `EFI/Boot/bootx64.efi` exist. Absence of Microsoft's signed loader/BCD fails closed. The EFI fallback presence is diagnostic only and does not unlock Windows, driver, WFP or GA. No guest policy or EFI variables are altered. No guest screenshot, source Windows files, boot secrets or image bytes are uploaded to CI artifacts.

It does **not** prove a complete Windows kernel boot, unattended Windows Setup/OOBE completion, EventLog service start, guest-initiated reboot or an operational WireGuardNT/WFP guest.

Repeated five-minute Q35/IDE boots did not progress the strict boot gate. The next one-shot experiment reuses the **same official free Microsoft VHD source and ephemeral QCOW2 policy** but changes only its QEMU guest disk controller to an emulated **NVMe PCIe controller** supported by Windows Server 2025's native storage stack and UEFI firmware. The QMP expected-disk check and fresh dual-event threshold remain mandatory and no full-guest success is asserted until CI passes. QEMU display/framebuffer is again **not** NT boot proof. Failure or no NVMe QEMU device fails closed; there is no fallback to the previously inconclusive IDE mode.

## Critical actual EVTX parser compatibility defect found before ISO fallback

The [R99 run #39117179656](https://github.com/Morandi-official/Oracle-Proxy-Infrastructure/actions/runs/39117179656) **failed**, but its expanded diagnostic identified **456 valid Windows event XML records**, including 70 from `Microsoft-Windows-Kernel-General`, 23 from `Microsoft-Windows-Kernel-Boot`, and 11 from `EventLog`. **All 456 TimeCreated values were rejected as unreadable** by the older verifier. The published Ubuntu/Debian `python-evtx` 0.7.4 source serializes binary SYSTEMTIME with `datetime.isoformat(' ')` — often an offset-naive, space-separated date/time. The older R99 verifier unconditionally demanded `SystemTime.endswith('Z')`, so it could discard correctly identified kernel/eventlog boot records before checking their IDs. Therefore its zero-recognized-event verdict was not enough to conclude an OS startup failure.

R99 now accepts only an exact ISO-8601 UTC serialization with `Z`, `+00:00`, or the documented python-evtx offset-naive `YYYY-MM-DD HH:MM:SS[.fraction]` form. Only the last form is explicitly normalized to UTC because the underlying Windows `SystemTime` is a system event UTC timestamp; ambiguous locale strings, other offsets, missing fields and malformed dates still fail closed. Both the parser and the safe aggregate diagnostics call the **same** timestamp helper. Negative tests enforce no local timezone inference and reject `+09:00` and slash-formatted timestamps.

**Important:** fixing the diagnostic incompatibility is a code change, NOT verified native Windows boot. A new real official-VHD CI must still show fresh Kernel-General 12 and EventLog 6005 within the independently witnessed start/end window. The official ISO (R101) has now passed authentic-origin and UEFI/Setup/WIM inventory checks, and the limited no-network unattended answer-file contract (R102) has passed CI and merged, but their presence does not authorize real VPN/WFP or production release. Maintain R83 and GA #34 denial until genuine cross-host and WFP/UU testing.
